# Research Changelog

## 2026-09-18 — SCCR self-heal + D5 freeze for pre-print

- **SCCR pipeline was silently stalled.** The cloud tier (`research-data.yml`) had
  not published since 2026-09-17 11:12 and the local tracker is disabled by design,
  so the headline sat at a manual run's value. Added
  `tools/research/sccr_fallback.py`: if the committed `data/sccr.json` is older than
  2 h, it re-derives from the local capture DB; otherwise it is inert (never a
  second writer). Wired into `com.bsahi.collectors`. Refreshed 0.36238/139 ->
  **0.321889/140**, with `fee_allocation` and `sccr_sensitivity` following.
- **D5 clearnet census frozen at 0** with a measured rationale
  (`research/cgnat-containment-finding.md`): both available networks are CGNAT
  (mobile: symmetric, multi-egress; JioFiber: four stacked private hops). Every
  alternative path was tested and closed (port-forward, UPnP, NAT-PMP, IPv6, Tor
  identity, STUN/hole-punch, free sandboxes, Play-with-Docker, ngrok, zrok).
- New `tools/net/census.py` — unified, environment-adaptive census emitting
  DISTINCT / CONCURRENCY / CONTAINED with the strongest honest bound.
- New `tools/net/deploy_sentinel_remote.sh` — one-command deploy of the seeding
  sentinel to any public-IP host, for the moment one exists.


Dated changes to BSAHI's measurements, grades, and methods. Corrections are
recorded here with their cause. Newest first.

## 2026-09-17 — SCCR ownership resolved: the cloud is the single writer

- The SCCR is generated by **GitHub Actions** (`research-data.yml`, every 30 min):
  the public 24h fee endpoint → the live capture → `sccr_live.py --frozen` →
  `data/sccr*.json`. It is **Mac-independent by design** — the research tier stays
  fresh when this machine is off.
- The local `com.bsahi.sccr-tracker` launchd job (daily, live-DB mode) is
  **Disabled by design**, not broken. It would be a *second writer* of
  `sccr.json` and race the cloud. **Do not re-enable it without retiring the cloud
  writer first.** Earlier "runs daily locally" references were misleading and are
  corrected here and in `sccr_live_runner.js`.
- Consequence: `research-data.yml` now stages everything the chain writes —
  `sccr_sensitivity.json`, `fee_allocation.json`, `datasets.json`, the baked static
  HTML, and the tokenised `research/*.html` pages — and its rebase-conflict path
  covers the HTML. Previously it staged `sccr*.json` only, so the cloud wrote
  those artifacts and then discarded them.
- Local capture of the *other* metrics is owned by `com.bsahi.collectors`
  (see the same-day persistent-collector entry).

## 2026-09-17 — Persistent local collectors + a dataset staleness guard

- The population / per-block / UTXO instruments ran in plain `nohup` loops under
  `/tmp`: macOS clears `/tmp` on reboot, the loops died on logout, and nothing
  restarted them — so capture stopped silently while the site kept serving the
  last values. `node_census_capture.py` (the canonical N source) and
  `mining_concentration.py` had no scheduler at all.
- New `tools/agents/29-local-collectors.js` (launchd `com.bsahi.collectors`,
  every 15 min) runs each instrument on its own cadence from a `~/.bsahi` state
  file. Legacy `/tmp/supervise_*.sh` loops retired.
- `20-site-health-agent.js` now also checks dataset freshness against a
  tolerable-age table and raises the normal alert path — a dead collector can no
  longer present as HEALTHY. Exposed in `/data/site-health.json`.
- Fixed `node_census_capture.py`: `json.load(path)` passed a string where a file
  object is required, crashing on every cached Wayback file.
- Fixed a two-writer conflict on `data/mining_concentration.json`:
  `pool_concentration.py` (schema v2, MEASURED) is canonical; the legacy
  `mining_concentration.py` (v1 stub) now refuses to overwrite a v2 file.



## 2026-09-17 — Population thread: versioned snapshot + N single-source fix

  its provenance, the three quantities, the observed activity partition, and every
  contributing dataset). Drift in any slow-moving input is now detectable; the
  three re-sampled instruments are flagged as expected to move.

  reachable-node series, then the legacy addrman mirror). Cross-check now returns
  **ALL THREE IMPLEMENTATIONS AGREE**.
- Regenerated `data/reproduction_verification.json`: frozen-capture average
  **0.240641 -> 0.289645** (= x32000/26586), 155/155 heights matched, max
  per-block diff 5e-7, spec v2.1.1. `research/replicate.md` expected-value
  corrected and extended with the population-replication method.

## 2026-09-17 — node-count semantics correction

- **Incorrect framing removed.** The paper described `getnodeaddresses` returning
  **32,000** as a *lower bound on reachable nodes*. It is not: `getnodeaddresses
  32000` returns addresses from the node's **address manager** (learned via **addr
  gossip**) and 32,000 was the *requested ceiling*, returned in full. It is a lower
  bound on **gossiped addresses** — a set including stale/unreachable entries,
  sized by peer count and uptime — **not** a node count and **not** a bound on
  reachable nodes. Corrected in `model-spec.json`, `node_census.json`, the census
  agent, and the working paper (§5.4 and all dependent rows).
- **Measured reachable nodes: 26,586** (btcnodes crawl, 2026-09-16) — reported
  separately from the address sample.
- **Census tool switched to `getnodeaddresses 0`** (returns *all* known addresses,
  per Core docs) so the addrman size is exact rather than truncated at the request
  ceiling.
- **`N = 32,000` marked provisional / deprecated as a node count**; the SCCR value
  is unchanged pending Phase C (re-basing N on the observability model). N 32K ->
  26.6K would move the headline ~+20%; the direction is unchanged.
- New `data/verification_population.json` and `/research/verification-population`.
